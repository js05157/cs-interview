## 정의

TCP/IP는 인터넷 통신에 필요한 역할을 여러 계층으로 나눈 프로토콜 묶음입니다. 응용 메시지, 종단 간 전달, 네트워크 간 전달, 가까운 링크의 전달을 구분하면 통신 과정을 이해하기 쉽습니다.

## 설명

웹 요청은 HTTP 같은 응용 메시지에서 시작합니다. 전송 계층의 TCP·UDP는 포트 등으로 종단을 구분하고, IP는 목적지 주소와 라우팅을 바탕으로 다음 홉을 찾습니다. 링크 계층은 그 구간에서 사용할 프레임으로 전달합니다. 수신 측은 각 헤더를 처리하며 위 계층으로 데이터를 넘깁니다.

도메인·IP·포트·링크 주소는 같은 식별자가 아닙니다. 라우터를 지날 때 링크 헤더는 바뀌며 NAT에서는 IP나 포트도 변환될 수 있습니다. 원격 서버의 MAC 주소를 알아야만 인터넷에 접근하는 것은 아닙니다.

계층은 역할 구분을 위한 모델입니다. HTTP/3처럼 QUIC/UDP를 사용하는 경로도 있고, 프록시가 연결을 종료하면 앞뒤 구간을 따로 봐야 합니다.

## 적용 예시

URI에서 도메인·포트·경로를 구분하는 기존 예제입니다. 외부 API가 느릴 때도 이 구분을 바탕으로 DNS·연결·TLS·응답 시간을 나누어 확인합니다.

```java
import java.net.URI;

public class EndpointDemo {
    public static void main(String[] args) {
        URI uri = URI.create("https://example.com/orders?limit=1");
        int port = uri.getPort() == -1 ? 443 : uri.getPort();
        if (!uri.getHost().equals("example.com")) throw new AssertionError();
        if (port != 443 || !uri.getRawPath().equals("/orders")) throw new AssertionError();
    }
}
```

도메인·포트·경로를 구분하는 예제입니다. URI 파싱만으로 DNS 조회나 TCP 연결이 발생하지는 않습니다. 실제 패킷 전달을 검증하는 실험과 구분합니다.

## 정리

TCP/IP 계층은 통신의 서로 다른 책임을 나눕니다. 응용의 메시지 의미와 포트·IP·링크 전달을 구분하면 장애 지점을 좁힐 수 있습니다. 모든 헤더가 출발지에서 목적지까지 그대로 유지되는 것은 아닙니다. 실제 연결을 종료하는 프록시와 전송 프로토콜도 함께 확인해야 합니다.

<summary>Q1. HTTP 500을 받았는데 무조건 IP 라우팅 실패부터 의심해야 할까요?</summary>
<div class="cs-followup-answer">

</div>
</details>

<details class="cs-followup">
<summary>Q2. 서버 포트가 443이면 암호화가 보장될까요?</summary>
<div class="cs-followup-answer">
<p>443은 HTTPS의 기본 포트 관례입니다. 포트 번호만으로 실제 TLS 설정이나 서버 인증 성공을 증명할 수는 없습니다.</p>
</div>
</details>
