웹 서버 하나가 여러 요청을 처리할 때, 요청마다 서버 프로그램을 새로 실행하지는 않습니다. 이미 실행 중인 프로세스 안에서 여러 스레드가 일을 나눠 맡을 수 있습니다. 이 구조를 이해하려면 실행 흐름의 개수보다 먼저 **무엇을 공유하고 무엇을 분리하는지** 살펴봐야 합니다.

## 프로그램을 실행하면 생기는 경계

디스크에 있는 프로그램 파일 자체는 실행 중인 상태가 아닙니다. 운영체제가 프로그램을 실행하면 코드와 데이터를 담을 가상 주소 공간, 열린 파일 같은 자원, 실행 상태를 관리합니다. 이렇게 실행에 필요한 자원과 상태를 묶는 단위가 프로세스입니다.

서로 다른 프로세스는 보통 독립된 가상 주소 공간을 사용합니다. 프로세스 A에서 사용한 포인터 값이 프로세스 B에서도 같은 객체를 뜻하지 않습니다. 같은 실행 파일을 두 번 실행해도 두 프로세스의 가변 데이터는 기본적으로 별개입니다. 다만 이것이 모든 물리 메모리가 반드시 복제된다는 뜻은 아닙니다. 코드 페이지를 공유하거나, 공유 메모리를 명시적으로 연결할 수도 있습니다.

프로세스의 격리는 장애 범위를 나누는 데도 도움이 됩니다. 한 프로세스의 메모리 접근 오류가 다른 프로세스의 메모리를 곧바로 덮어쓰지 못하도록 운영체제와 하드웨어가 경계를 제공합니다. 그렇다고 별도 프로세스가 모든 장애를 차단하는 것은 아닙니다. 같은 DB나 파일, CPU와 메모리 같은 시스템 자원을 공유한다면 서로 영향을 줄 수 있습니다.

## 하나의 주소 공간에서 여러 흐름을 실행하기

스레드는 프로세스 안의 실행 흐름입니다. 일반적인 OS 스레드는 각자의 프로그램 카운터와 레지스터 상태, 스택을 갖습니다. 같은 프로세스의 스레드들은 힙과 전역 데이터, 열린 파일 등 프로세스 자원을 공유합니다.

![프로세스 A의 두 스레드는 각자 스택과 실행 상태를 갖고 같은 힙 객체를 참조한다. 프로세스 B의 가상 주소 공간은 기본적으로 분리된다.](https://raw.githubusercontent.com/js05157/cs-interview/master/blog/assets/diagrams/process-thread.svg)

그림의 스택 분리는 실행 중인 메서드의 호출 상태를 따로 관리한다는 뜻입니다. 스택 안의 지역 변수에 객체 참조가 들어 있다면, 그 참조는 다른 스레드가 사용하는 객체를 가리킬 수 있습니다. **지역 변수의 위치와 객체의 공유 여부는 별개**입니다. 또 다른 스레드의 스택에 있는 데이터가 하드웨어적으로 접근 불가능하다는 뜻도 아닙니다. 스택 역시 같은 프로세스의 주소 공간 안에 있습니다.

운영체제는 실행 가능한 스레드를 CPU에 배치합니다. 단일 코어에서는 여러 흐름을 번갈아 진행해 동시성을 제공할 수 있습니다. 여러 코어에서는 실제로 같은 시간에 실행하는 병렬성도 가능합니다. 스레드가 두 개라는 사실만으로 병렬 실행이나 두 배의 속도를 보장하지는 않습니다.

여기서는 일반적인 OS 스레드와 Java 17의 플랫폼 스레드 예제를 다룹니다. JVM 스레드의 모든 실행 모델이 OS 스레드와 일대일로 대응하는 것은 아닙니다. 예를 들어 Java 21의 가상 스레드는 JVM이 스케줄링하며 플랫폼 스레드와 구분해야 합니다.

## 두 스레드가 같은 카운터를 바꾼다면

다음 Java 17 예제에서는 두 스레드가 하나의 `AtomicInteger`를 공유하고 각각 10,000번 증가시킵니다.

```java
import java.util.concurrent.atomic.AtomicInteger;

public class ProcessThreadDemo {
    public static void main(String[] args) throws InterruptedException {
        AtomicInteger count = new AtomicInteger();
        Runnable work = () -> {
            for (int i = 0; i < 10000; i++) count.incrementAndGet();
        };
        Thread a = new Thread(work);
        Thread b = new Thread(work);
        a.start(); b.start();
        a.join(); b.join();
        if (count.get() != 20000) throw new AssertionError(count.get());
        System.out.println(count.get());
    }
}
```

실행 결과는 다음과 같습니다.

```text
20000
```

`work`는 하나의 `count` 객체를 참조합니다. 두 스레드가 같은 `Runnable`을 실행하므로 같은 카운터에 접근합니다. `start()`가 새 실행 흐름을 시작하고, `join()`은 대상 스레드가 종료할 때까지 기다립니다. 메인 스레드는 두 작업이 모두 끝난 뒤 결과를 확인합니다.

일반적인 `count++`는 값을 읽고, 1을 더하고, 다시 쓰는 과정을 하나의 원자적 연산으로 보장하지 않습니다. 두 스레드가 같은 이전 값을 읽고 같은 결과를 덮어쓰면 증가가 유실될 수 있습니다. 이 예제의 `incrementAndGet()`은 증가를 원자적으로 수행합니다. `volatile int`만으로 바꾸면 가시성은 다루더라도 복합 연산인 증가의 원자성은 얻지 못합니다.

이 실행은 공유 카운터의 결과를 검증합니다. 처리 속도나 실제 코어 배치, 병렬 실행 비율을 측정하지 않습니다. 또한 원자적 카운터 하나가 안전하다고 여러 필드 사이의 불변 조건이나 전체 비즈니스 로직까지 원자적으로 처리되는 것은 아닙니다.

## 공유할수록 통신은 쉬워지고 조정은 필요해진다

| 선택 기준 | 서로 다른 프로세스 | 같은 프로세스의 스레드 |
| --- | --- | --- |
| 주소 공간 | 기본적으로 독립, 명시적 공유 가능 | 같은 주소 공간 사용 |
| 데이터 전달 | 소켓·파이프·공유 메모리 등 IPC 사용 | 같은 객체를 참조할 수 있음 |
| 조정할 문제 | 통신 실패·직렬화·자원 소유권 | 경쟁 상태·가시성·락 경합 |
| 장애 범위 | 메모리 격리 경계를 만들기 쉬움 | 메모리 손상·자원 고갈이 프로세스 전체에 영향 가능 |

같은 힙을 공유하면 데이터를 별도로 전달하지 않고도 함께 사용할 수 있습니다. 대신 누가 언제 값을 읽고 바꾸는지 조정해야 합니다. 프로세스를 분리하면 통신과 운영 비용이 늘 수 있지만 장애 격리와 독립적인 수명 주기를 얻을 수 있습니다. 어느 방식이 항상 더 빠르거나 더 안전하다고 단정하기보다 실제 작업과 실패 모델을 비교해야 합니다.

Java에서 한 작업 스레드가 처리되지 않은 예외로 끝나더라도 JVM 전체가 반드시 종료되는 것은 아닙니다. 반면 네이티브 코드의 메모리 손상이나 프로세스 수준의 자원 고갈은 더 넓은 영향을 줄 수 있습니다. 예외 처리 경계와 프로세스 격리 경계도 구분해야 합니다.

## 서버의 공유 상태를 설계할 때

여러 요청 처리 스레드가 같은 Spring 싱글턴 서비스 객체를 참조할 수 있습니다. 싱글턴은 객체의 생성·공유 범위를 설명할 뿐, 가변 필드를 안전하게 보호해 주지는 않습니다. 요청별 데이터를 서비스 필드에 덮어쓰는 구조라면 서로 다른 요청의 값이 섞일 수 있습니다. 요청별 상태는 가능한 한 호출 범위에 두고, 공유가 필요하면 불변 데이터나 목적에 맞는 동기화 수단을 선택합니다.

동시성의 크기도 별도의 설계 문제입니다. 요청마다 스레드를 무한 생성하면 CPU뿐 아니라 스택 메모리, 락, DB 커넥션 같은 한정된 자원에서 병목이 생깁니다. 작업의 CPU 사용량과 I/O 대기, 외부 시스템의 처리 한도를 보고 스레드 풀과 대기열을 제한해야 합니다. 강한 장애 격리가 필요한 작업은 별도 프로세스나 서비스로 나누는 비용을 함께 검토합니다.
