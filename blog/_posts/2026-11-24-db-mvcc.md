## 정의

MVCC는 데이터의 여러 버전과 가시성 규칙을 사용해 동시 읽기를 처리하는 방식입니다. 각 조회가 볼 버전을 고르므로 쓰기가 진행 중이어도 이전의 일관된 상태를 읽을 수 있습니다.

## 설명

PostgreSQL 17에서는 갱신된 행의 버전과 트랜잭션 정보를 이용해 어떤 조회에 보일지 판단합니다. 새 커밋이 생겨도 기존 스냅샷은 이전 버전을 볼 수 있고, 관련 조회에 더 이상 필요 없는 버전은 VACUUM 같은 유지 관리로 정리합니다.

오래된 스냅샷이 필요한 버전을 즉시 없앨 수는 없습니다. 그래서 긴 트랜잭션은 정리를 늦추고 저장 공간과 유지 비용을 늘릴 수 있습니다.

MVCC가 락을 모두 없애지는 않습니다. 쓰기끼리의 충돌이나 DDL 대기는 남으며 스냅샷의 수명도 격리 수준에 따라 다릅니다. xmin/xmax 같은 내부 정보를 영구적인 업무 버전 ID로 사용하지 않습니다.

## 적용 예시

PostgreSQL 두 연결에서 기존 스냅샷과 새 조회가 서로 다른 값을 보는 순서를 확인합니다. 행의 물리 배치나 VACUUM 성능을 측정하는 실험은 아닙니다.

```sql
-- session: setup
CREATE TABLE version_demo (id integer PRIMARY KEY, amount integer NOT NULL);
INSERT INTO version_demo VALUES (1, 10);
```

```sql
-- session: A
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT id, amount, xmin::text FROM version_demo WHERE id = 1;
```

```sql
-- session: B
UPDATE version_demo SET amount = 20 WHERE id = 1;
DO $$ BEGIN
    ASSERT (SELECT amount FROM version_demo WHERE id = 1) = 20;
END $$;
```

```sql
-- session: A
DO $$ BEGIN
    ASSERT (SELECT amount FROM version_demo WHERE id = 1) = 10;
END $$;
COMMIT;
DO $$ BEGIN
    ASSERT (SELECT amount FROM version_demo WHERE id = 1) = 20;
END $$;
```

서로 다른 스냅샷에서 관측 결과가 달라지는 것을 확인합니다. 디스크의 행 배치나 VACUUM 성능을 측정한 실험은 아닙니다.

## 정리

MVCC는 조회마다 보일 데이터 버전을 선택해 동시성을 돕습니다. 이전 스냅샷이 필요한 버전은 당장 정리할 수 없습니다. 따라서 읽기 경쟁을 줄이는 대신 버전 저장과 정리 비용을 관리해야 합니다. MVCC가 있어도 쓰기 충돌과 모든 업무 경쟁이 사라지는 것은 아닙니다.

## 꼬리 질문


<details class="cs-followup">
<summary>Q1. 오래된 스냅샷이 남아 있으면 왜 VACUUM의 정리가 늦어질까요?</summary>
<div class="cs-followup-answer">
<p>그 조회가 아직 읽을 수 있는 이전 버전이 필요하기 때문입니다. 너무 일찍 지우면 같은 스냅샷의 올바른 읽기를 유지할 수 없습니다.</p>
</div>
</details>

<details class="cs-followup">
<summary>Q2. MVCC를 쓰는 DB에서도 쓰기 작업이 기다릴 수 있을까요?</summary>
<div class="cs-followup-answer">
<p>가능합니다. 같은 행의 갱신 충돌이나 명시적 잠금 등은 MVCC의 일반 읽기 처리와 별개의 경쟁입니다.</p>
</div>
</details>
